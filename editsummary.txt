HOW TO UPLOAD A CSV TO AN EXISTING FOUNDRY DATASET (learned the hard way)
------------------------------------------------------------------------
1. Upload atomically with the v1 endpoint. It opens, uploads and commits in
   one call:
     POST /api/v1/datasets/{rid}/files:upload
          ?filePath=NAME.csv&transactionType=SNAPSHOT
   SNAPSHOT replaces dataset contents, so there is no append/duplication risk.

   Do NOT use the v2 three-step flow (create transaction, PUT file, commit).
   The v2 file PUT path 404s, and committing afterwards commits an EMPTY
   snapshot, which wipes the dataset. That happened to station.csv here and was
   restored about 30 seconds later. The rule: never commit a transaction
   without checking the upload into it returned 200.

2. A raw file upload does NOT carry a schema. The UI upload does two things,
   infer a schema and store the file; the API upload only does the second. With
   no schema the object type reports "schema mismatch between this object type
   and its backing datasource" and refuses to index, while continuing to serve
   its last good index. Dataset looks right, ontology serves stale data.

   Re-apply with PUT /api/v1/datasets/{rid}/schema?branchId=master&preview=true
   Read the expected types off the object type first
   (GET /api/v2/ontologies/{ont}/objectTypes/{Type}) and mirror them exactly
   rather than letting Foundry re-infer.

3. recordDelimiter MUST match the bytes on disk. Python's csv.writer emits
   CRLF, not LF. Setting "\n" makes Spark refuse the file:
     "\n has been set in the schema and \r\n has been detected in the file"
   Omitting the key does NOT fall back to permissive; it defaults to "\n".
   Set it explicitly to "\r\n".

   This surfaced as Funnel:InvalidInputDataset on the Background Changelog
   build, which is a useless error on its own. The readable one comes from
     GET /api/v2/datasets/{rid}/readTable?format=CSV&branchName=master&preview=true
   That endpoint is the fastest way to tell whether a dataset is actually
   parseable, and should be the first check after any API upload.

4. After fixing the schema, the object type may still need a manual reindex:
   Ontology Manager > object type > Datasources > Live pipeline "..." > Reindex.
   Supplier recovered on its own; station and part needed the manual trigger.

Note: generate.py still writes CRLF and the stored schemas now say "\r\n", so
the two are consistent. If generate.py is ever changed to LF, the three schemas
must be updated to match or parsing breaks again.

THREE THINGS LEARNED
--------------------
1. Creating action types does not put them in the SDK. They must be added in
   Developer Console > Ontology SDK > Resources > Action types, then a new SDK
   version generated. Published 0.2.0.

2. Vite pre-bundles dependencies and caches them. After installing the new SDK
   the browser threw "does not provide an export named 'acknowledgeShortage'"
   while tsc passed, because TypeScript read the real package and Vite served
   the stale 0.1.0 bundle. Fix: rm -rf node_modules/.vite and restart.

3. The date parameters are LocalDate, NOT instants. Appending T00:00:00Z to be
   "safe about timezones" is rejected with InvalidParameterValue. A LocalDate
   has no timezone to get wrong — a delivery date is a day on a calendar, not a
   moment. This is why the read path must normalize to UTC and the write path
   must not. The generated .d.ts labels these `datetime`, which is misleading;
   the server is the authority.

   Diagnosed by applying the action with curl against
   POST /api/v2/ontologies/{ont}/actions/{apiName}/apply, which returns the
   parameterBaseType in the error. Much faster than guessing from the browser.

PIPELINE (pipeline/) — four PySpark transforms for a Foundry Code Repository:
    clean_station.py       types + over_takt_days + is_bottleneck
    clean_aircraft.py      types + slip_days, joined to station name
    part_cover.py          stock cover = on hand / per airframe
    shortage_enriched.py   the showpiece join, one row per shortage reaching
                           part, supplier, work order, aircraft and station

  THE DESIGN RULE, and the thing worth defending: the pipeline computes what is
  stable, the client computes what depends on "now". Slip days, over-takt,
  exposure and cover are stored facts and belong in Spark. "Is this tail
  overdue", "days past forecast" and "days to recovery" depend on today — a
  nightly build would make them wrong every morning until it ran, confidently
  and invisibly. Those stay in derive.ts, which takes asOf as an argument and
  is tested against it. So derive.ts is not made redundant by the pipeline;
  the split is principled.

  shortage_enriched duplicates the join useOperations.ts does in TypeScript.
  Deliberate: the client version must exist so an applied action updates the
  screen immediately; the Spark version is what anything else consumes without
  re-deriving it differently. Being able to explain when to choose each is the
  point of having both.

  VERIFIED LOCALLY, not just written. pipeline/run_locally.py stubs
  transforms.api and runs the identical functions on a local Spark against
  data/*.csv — all 4 produce output and pass validations.
  pipeline/test_validations.py corrupts the data 8 ways and asserts each
  transform refuses: duplicate station code, sequence gap, zero takt, unknown
  aircraft status, forecast before build start, undelivered aircraft with no
  station, shortage referencing a missing part, and a duplicate part inflating
  the join. 8 of 8 fire. Both run in CI.
